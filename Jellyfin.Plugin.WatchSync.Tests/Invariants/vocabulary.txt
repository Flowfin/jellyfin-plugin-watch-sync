# The rules this guard refuses in the plugin's own sources, one per line.
#
# Fields are separated by " :: ": the identifier, the invariant it belongs to, the
# issue that introduced the invariant, the regular expression, what a call matching it
# does, and what to reach for instead.
#
# An invariant is carried by one or more rules. Storage identity is five rules in the
# guard beside this one, for the five ways a key can be derived from where a file is
# kept, and the same reasoning applies here: a separate identifier per way is what
# lets a finding say which mistake was made and lets a departure cover one call
# without covering the rest.
#
# This is data rather than source for the reason the two vocabularies already in the
# tree are. A scanner carrying these literals in a .cs file inside a scanned project
# would match itself, and the exclusion repairing that would be a hole in the middle
# of the guard. This one scans the plugin project and lives in the test project, so
# the self-match is not possible today and stays impossible if the two ever meet.
#
# What these patterns cannot see is written in docs/invariants.md rather than here,
# because it is the first thing a reader deciding whether to trust a green run needs
# and the last thing they would find in a data file.

# One person's watch history landing in another person's account is the worst outcome
# available to this plugin. The mapping is an operator decision the pairing plugin
# owns, and a name comparison is the inference #42 refuses.
user-name-equality :: mapping-not-inferred :: 42 :: \.Username\b\s*(==|!=)|(==|!=)\s*[A-Za-z_][A-Za-z0-9_.]*\.Username\b :: decides who a change belongs to by comparing two names :: the mapping the pairing plugin hands over, which names the local user outright
user-name-equals-call :: mapping-not-inferred :: 42 :: \.Username\s*\.\s*Equals\s*\(|Equals\s*\([^\n]*\.Username\b :: decides who a change belongs to by comparing two names :: the mapping the pairing plugin hands over, which names the local user outright
user-name-search :: mapping-not-inferred :: 42 :: (FirstOrDefault|SingleOrDefault|LastOrDefault|Any|Where|Single|First)\s*\([^\n]*\.Username\b :: finds a local user by the name a peer sent :: the mapping the pairing plugin hands over, which names the local user outright

# A log is a file that gets copied into a support thread. #67 permits an item
# identifier at the ordinary level and permits a title at no level at all, so what
# these refuse is not narrower than what that issue allows.
log-item-title :: log-holds-no-viewing :: 67 :: Log(Trace|Debug|Information|Warning|Error|Critical)\s*\([^\n]*\.(Name|OriginalTitle|SortName|ForcedSortName)\b :: writes the title of a work somebody watched into a log :: the match key, which names the item to an operator without naming the work

# The template holds the plugin in a static and reaches for it from anywhere, which is the
# shape #8 refuses on the first day. A type that reaches for it stops being constructible
# in a test, because the static holds nothing until a server has loaded the plugin, and
# that is the whole reason the queue, the matcher and the resolver are wanted behind
# constructors instead.
plugin-instance-read :: static-instance-not-read :: 8 :: \bPlugin\s*\.\s*Instance\b :: reaches the plugin's static instance from a type that was handed nothing :: the dependency taken through the constructor, so the type can be built in a test with no server present

# Whether a send that timed out is ever repeated is not this plugin's to decide, so
# #50 takes the pessimistic answer and makes a second delivery indistinguishable from
# the first. The mechanism is the write itself: an apply that assigns is idempotent
# whatever arrives twice, and an apply that adds is not. The set of recently seen
# envelopes that issue also asks for only bounds the window in which the addition is
# invisible, which is why these rules are on the operator rather than on the set.
play-count-increment :: applied-change-is-assigned :: 50 :: \.PlayCount\s*(\+\+|\+=) :: adds a play to whatever the record holds at the moment of the write :: the count reconciled against the agreed record and then assigned, which is #33
play-count-pre-increment :: applied-change-is-assigned :: 50 :: \+\+\s*[A-Za-z_][A-Za-z0-9_.]*\.PlayCount\b :: the same addition, spelled the other way round :: the count reconciled against the agreed record and then assigned, which is #33
position-accumulated :: applied-change-is-assigned :: 50 :: \.PlaybackPositionTicks\s*(\+\+|\+=) :: adds to the stored position instead of assigning the point the person stopped at :: the position the change carries, assigned

# Reading a clock and waiting on one are different mistakes, and only the first has
# names above. #16 suppresses the echo with a window around this plugin's own write, and
# a window held open by real elapsed time cannot be closed by a test at all: the ten
# exchanges that issue asks for after one change become ten real waits, which is slow,
# then flaky on a loaded machine, and then deleted. The suite half is already refused by
# the headless vocabulary; these rules are the plugin half, which is where the waiting
# decides whether an echo leaves again.
wait-thread-sleep :: waiting-is-on-the-injected-clock :: 16 :: Thread\.Sleep\b :: stops the thread for a span nothing in a test can advance :: the injected clock, asked whether the window has closed
wait-spin :: waiting-is-on-the-injected-clock :: 16 :: \bSpinWait\b :: burns real elapsed time and holds a processor while it does :: the injected clock, asked whether the window has closed
wait-task-delay :: waiting-is-on-the-injected-clock :: 16 :: Task\.Delay\b :: waits until the machine says the span has passed rather than until the caller says so :: the injected clock, asked whether the window has closed
wait-timer :: waiting-is-on-the-injected-clock :: 16 :: new\s+(System\.Threading\.)?(Periodic)?Timer\s*\( :: fires on real elapsed time, so a window, a backoff or a sweep runs when the machine says so :: a timer created from the injected clock

# The interface this plugin reads and writes user data through is not the same on the two
# supported lines, so #20 holds the difference in one adapter of this plugin's own. The
# bullet with teeth there is the last one, that no type outside the adapter references the

# somewhere else, and by then the adapter is a refactor rather than a design.

# This plugin holds no pairing, no key and no user mapping, and every one of the three
# comes from another plugin. #40 puts that contract behind one interface of this plugin's
# own, and the bullet with teeth there is that no other type in this plugin references the
# pairing plugin's types. It has to be true from the first call rather than reached later:
# a scan that passes today keeps passing while the first call site is written somewhere
# else, and by then the adapter is a refactor across every caller rather than a decision
# taken once. The last rule is not about the adapter at all, because there is no place in
# this plugin where key material may appear.
pairing-namespace :: pairing-behind-the-adapter :: 40 :: \bJellyfin\.Plugin\.ServerPairing\b :: names the pairing plugin's namespace, in a using directive or in a qualified name :: this plugin's own interface, which carries what the contract offers and nothing else
pairing-contract-interface :: pairing-behind-the-adapter :: 40 :: \b(IPairedPeers|IPairingKeySource|IPairingKeyStore|IPairingRecordStore)\b :: takes one of the pairing plugin's own interfaces as a dependency :: this plugin's own interface, so the contract's shape reaches one type here rather than every caller
pairing-protocol-type :: pairing-behind-the-adapter :: 40 :: \b(PairingRecord|PairingState|PairingMessage|PeerChannel|PeerReply)\b :: reaches a type of the pairing plugin's protocol, whose shape that board decides and may change :: this plugin's own types, which the adapter answers in
