# Which facts drive which row of the conflict table, one entry per row.
#
# Five fields per entry, separated by " :: ":
#   the field the row is about :: its state :: the test classes that drive it ::
#   the types in the resolver that decide it :: the reason
#
# The two list columns are comma separated and "-" means none.
#
# The states are:
#
#   covered  a rule in the resolver decides the row and the named classes drive it
#   awaited  no rule decides the row yet, and the reason says what has to land first
#
# ConflictRowCoverageTests holds this file to docs/conflicts.md in both directions and
# to the tree in both directions. A row of the table with no entry here fails, which is
# the first condition of #81 and the reason the file exists: a row added to the table
# with nothing driving it is a rule an operator's history is answered by and no fact
# ever executes. An entry naming a field the table has no row for fails as well, so a
# row taken out of the table takes its entry with it rather than leaving one behind.
#
# The awaited state is the one that has to fail closed, and the type column is what
# makes it. A row cannot be declared awaited and also name a class or a type, and every
# public type the resolver holds is named by exactly one entry, so the day a rule lands
# for an awaited row the type it arrives as belongs to no entry and this goes red. That
# is deliberately not keyed on the name anybody predicted for it, because a register
# that only notices the name it guessed is one that notices nothing.
#
# THAT DAY ARRIVED AND THE MECHANISM IS WHAT CAUGHT IT. LastPlayedMaximum and
# LastPlayedAnswer were written before this entry was, and EveryTypeInTheResolverBelongsToOneEntry
# was the one fact that reddened, naming both types. Every entry is covered today, so the
# state exists in this file's vocabulary and in no entry, which is the state to leave it
# in: a vocabulary that shrank to what is currently in use would have to be widened again
# by whoever adds the next row of the table.
#
# What it cannot see, stated rather than left to be discovered. It reads which classes
# are named and that they hold facts, and never whether a fact drives the row it is
# filed under, so a class renamed onto the wrong row passes. Conflict/removal.txt is what
# reaches that, which is the second condition of #81: it records, per row, the change that
# takes the rule out and the facts that reddened, and ConflictRuleRemovalTests requires
# every fact it names to sit in a class THIS file files under THAT row. So which facts are
# a row's own is decided here rather than by whoever wrote the removal entry, and a rule
# whose removal reaches another row's class reddens. The removal itself is applied by hand
# and reverted, and nothing in this suite or in any workflow of this repository runs one.
#
# The third condition is met for the rows that have a rule. Conflict/ordered-pairs.txt
# declares the states each of those rows can hold and walks every ordered pair of them
# with the answer in the data, and ConflictOrderedPairTests requires the fields it walks
# to be exactly the fields entered here as covered. So this register decides which rows
# that walk is owed for, and a row moving from awaited to covered leaves the walk
# missing a field rather than leaving it unnoticed.
#
# Blank lines and lines beginning with # are ignored.

Played :: covered :: PlayedRatchetTests, ConflictOrderedPairTests :: PlayedRatchet, RatchetAnswer :: The ratchet, which is #31. It answers on the two played states alone and reads the two dates without deciding on them, so its facts are about a completion holding against a position however much newer the position is.
PlayCount :: covered :: PlayCountReconciliationTests, ConflictOrderedPairTests :: PlayCountReconciliation, PlayCountAnswer :: The reckoning against what two sides last agreed, which is #33. Its facts are about a pair over a sequence of exchanges rather than about one answer, because adding the two counts is only visibly wrong after a while.
PlaybackPositionTicks :: covered :: PositionRecencyTests, ConflictOrderedPairTests :: PositionRecency, PositionAnswer :: The later play bounded by the tolerated clock skew, which is #32. Its facts are about two clocks rather than about two positions, and the two halves of the rule fail apart: a rule that stopped bounding the comparison reddens the fact about a margin inside the tolerance and nothing else, and a rule that answered every pair with the greater position reddens the three facts about the comparison and leaves the tie ones green. The setting the tolerance is chosen with is still #58, and the two numbers it is bounded by are declared by the type rather than by docs/conflicts.md.
LastPlayedDate :: covered :: LastPlayedMaximumTests, ConflictOrderedPairTests :: LastPlayedMaximum, LastPlayedAnswer :: The later of the two dates, which is the row this table declared and the sources decided nowhere. No issue on this board writes it: every issue naming the field is #1, #12, #14, #30 and #35, and #30 is the table, #12 the moved set and #14 the agreed record, so it arrives with #81 rather than with a rule issue of its own. Its facts are about a pair of moments and nothing else, because the row's evidence column is both dates and nothing else, and the states they are driven with give the later date to the side that is not played, holds no plays and carries the greater position.
